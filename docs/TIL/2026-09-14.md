# 2026-09-14 TIL — 마이크 입력부터 음성 인식 설계까지

> 2일 차 대화와 실제 작업을 바탕으로 Codex가 작성한 복습 초안이다. 사용자가 나중에 자신의 표현으로 수정할 문서이며, 설명을 들었다는 사실을 개념을 숙달했다는 의미로 기록하지 않는다.

## 오늘 직접 확인한 것

Codex가 마이크 입력과 음성 수집 기능을 구현하고 빌드·검사를 수행했다. 나는 앱에서 마이크를 선택하고 시작·종료 버튼을 눌러 소리에 따라 음량 막대가 움직이는 것을 확인했다.

이후 ‘수집한 음성 지우기 → 마이크 시작 → 마이크 종료 → 음성 지우기’를 직접 시험했다. 화면은 수집 없음 → 입력 중 → 12.0초·4503.8 KiB 수집 완료 → 수집 없음 순서로 바뀌었다. 이것은 화면과 조작 흐름을 확인한 것이며, 녹음 재생이나 음성 인식 정확도를 확인한 것은 아니다.

## 음량 측정, 녹음, 음성 인식은 서로 다르다

첫 기능은 마이크 소리의 크기를 계산해 막대를 움직이는 것이었다. 막대가 움직인다는 사실만으로 녹음 데이터가 남는 것은 아니다.

다음 기능에서 시작부터 종료까지 음성을 메모리에 모으도록 확장했다. 종료하면 WAV 형식의 바이트 데이터가 남는다. WAV라고 해서 반드시 디스크에 `.wav` 파일이 만들어지는 것은 아니다. 지금은 파일 저장 없이 메모리에만 보관한다.

음성 인식은 이 소리를 한국어 문장 같은 텍스트로 바꾸는 별도 단계다. 오늘은 아직 연결하지 않았다. 기존 ‘예시 문장 보기’는 고정 문장을 보여주므로 녹음 결과와 관계없다.

```text
현재 구현: 마이크 → 음량 표시 + 메모리 수집 → 종료 → WAV 데이터 보관
다음 단계: WAV 데이터 → 음성 인식 → 한국어 원문
후속 단계: 한국어 원문 → 외국어 번역·한글 발음 생성 → 화면 표시
```

## 지금 음성은 언제 없어지는가

- 수집한 음성 지우기를 누를 때
- 새 마이크 입력을 시작할 때
- 앱 창을 닫을 때

최신 입력 하나만 보관하며, 이전 입력을 쌓아 두지 않는다. 최대 입력은 60초 또는 원시 오디오 16 MiB다. WAV를 만드는 동안 복사 데이터도 생기므로 프로그램 전체 메모리가 16 MiB 이하라는 뜻은 아니다. 운영체제 수준의 완전한 보안 삭제를 보장한다는 의미도 아니다.

## API와 로컬 인식 중 무엇을 고를까

API 방식은 음성을 서버에 보내 서버가 인식 계산을 수행한다. 내 PC 부담은 줄지만 녹음·전송 자원은 여전히 필요하며, 인터넷·서버 지연과 사용료가 있다. ChatGPT 구독료와 앱에서 호출하는 API 요금은 별개다. 오늘 앱에서는 유료 API를 호출하지 않았다.

로컬 방식은 내 PC에서 모델을 실행한다. 음성 인식 API 사용료는 없지만 모델 다운로드 공간과 CPU·GPU·메모리가 필요하다. 게임과 자원을 공유하므로 게임 프레임이나 인식 속도에 영향이 있을 수 있다. 이 현상을 네트워크 핑과 같은 것으로 보지는 않는다.

Windows Live Captions를 비교 대상으로 검토했고, Windows AI 음성 인식 API와 whisper.net을 로컬 후보로 이야기했다. 기존 자막창에서 글자를 가져오는 방법과 우리 앱이 직접 인식 엔진을 사용하는 방법은 다르다. 아직 모델을 설치하거나 후보의 한국어 정확도·속도를 측정하지 않았다.

가격과 지원 환경은 바뀔 수 있으므로 실제 연결 시 다시 확인한다. 참고 자료:

- [OpenAI의 ChatGPT/API 별도 결제 안내](https://help.openai.com/en/articles/9039756-managing-billing-settings-on-the-chatgpt-web-and-api-platform)
- [Windows Live Captions](https://support.microsoft.com/en-us/accessibility/windows/use-live-captions-to-better-understand-audio)
- [Windows AI 음성 인식 API](https://learn.microsoft.com/en-us/windows/ai/apis/speech-recognition)
- [whisper.net](https://github.com/sandrohanea/whisper.net)

## 나중에 인식 방식을 바꾸면 전체 코드를 다시 만들어야 할까

인식 부분을 공통 인터페이스 뒤로 분리하면 녹음·화면·후속 번역 코드를 대부분 유지할 수 있다. API 인증과 통신 오류, 로컬 모델 설치와 메모리 부족처럼 방식마다 다른 처리는 각 구현이 맡는다.

```text
녹음 → 공통 음성 인식 창구 → 로컬 또는 API → 한국어 원문 → 후속 번역
```

이 구조는 오늘 합의한 다음 개발 방향이며 아직 구현하지 않았다. 두 엔진을 한꺼번에 개발하지도 않는다. 오히려 ‘종료 후 한 번 인식’에서 ‘말하는 중 계속 인식’으로 바꾸면 임시 문장 갱신과 번역 시점까지 바뀌므로 영향 범위가 커질 수 있다.

## 제품을 만들며 다시 확인할 것

- 내 한국어 말하기부터 영어 결과를 읽고 말하기까지 걸리는 전체 시간이 게임에서 쓸 만한가?
- 앱 입력 버튼과 게임 마이크 음소거 상태를 혼동하지 않는가?
- 게임 소리에는 효과음과 음악이 섞이는데 상대 발화를 제대로 인식할 수 있는가?
- 로컬 인식이 게임 성능에 주는 영향과 API의 실제 사용 비용은 어느 정도인가?
- 음성 인식이 성공해도 번역과 한글 발음은 별도로 검증해야 하지 않는가?

현재는 단순한 시작·종료 버튼부터 쌓아가기로 했다. 게임 음소거 연동, 전역 단축키, 실시간 인식은 나중에 확장한다.
