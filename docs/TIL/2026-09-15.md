# 2026-09-15 TIL — 로컬 음성 인식·번역 연결과 오류를 나눠 보기

> 3일 차 실제 작업과 대화를 바탕으로 Codex가 작성한 복습 초안이다. 사용자가 나중에 자신의 표현으로 수정할 문서다. 직접 확인한 사실, 코드로 확인한 동작, 아직 추정인 원인을 구분했다.

## 오늘 어디까지 만들었나

어제는 마이크 소리를 메모리에 수집했다. 오늘은 그 음성을 한국어로 인식하고, 원문을 수정한 뒤 영어 번역과 한글 발음을 요청하는 흐름을 연결했다.

```text
마이크 입력 → 메모리의 음성
                  ↓ Whisper
             한국어 원문 → 직접 수정 가능
                  ↓ 번역하기
             Ollama의 LLM → 영어 문장
                  ↓ 같은 LLM에 별도 요청
             한글 발음 → 형식 검사 → 영어·발음 함께 표시
```

코드 작성·설치·자동 검사는 Codex가 수행했다. 나는 앱에서 직접 말하고, 인식된 원문을 고치고, 다시 인식과 번역을 실행해 결과를 확인했다. 화면이 완성됐다는 사실과 인식·번역의 품질이 충분하다는 것은 서로 다르다.

## Whisper와 Ollama, Qwen의 역할

| 이름 | 읽는 법·뜻 | 이번 앱에서 하는 일 |
| --- | --- | --- |
| Whisper | 위스퍼, 음성 인식 모델 | 음성을 한국어 글자로 변환 |
| whisper.net | 위스퍼 닷넷, C#에서 Whisper를 사용하는 라이브러리 | 녹음 데이터를 모델에 전달하고 결과를 받음 |
| Ollama | 올라마, 로컬 모델 실행 도구 | 내 PC에서 번역용 언어 모델을 실행 |
| Qwen3 | 큐웬 쓰리, 언어 모델 계열 | 한국어를 영어로 번역하고 한글 발음을 생성 |
| LLM | 엘엘엠, 대규모 언어 모델 | 지시와 입력 문맥에 따라 텍스트를 생성 |
| 4B / 8B | 포 비 / 에이트 비, 약 40억 / 80억 매개변수 규모 | 모델 크기의 구분. 숫자가 커도 모든 결과가 정확해지는 것은 아님 |

현재 Whisper는 다국어 base를, 번역은 Qwen3 8B를 기본값으로 사용한다. 4B도 비교용으로 설치돼 있다. **둘 다 최종 번역 모델로 확정한 것이 아니다.** 추후 다른 로컬 모델과 외부 API를 비교할 예정이다.

Ollama와 통신할 때 HTTP라는 방식을 사용하지만 주소는 `127.0.0.1`이다. 이는 내 PC 자신을 가리킨다. 따라서 이번 요청은 외부 유료 AI 서버로 보내는 API 호출과 다르다. 음성 인식은 앱 안에서, 번역용 텍스트 처리는 PC 안의 Ollama에서 수행한다.

## ‘녹음 다시 인식’은 더 좋은 답을 자동으로 만드는 버튼이 아니다

이 버튼은 메모리에 남아 있는 같은 녹음을 다시 Whisper에 전달한다. 새로 마이크를 켜거나 더 큰 모델로 자동 전환하지 않는다. 같은 모델과 설정이면 같은 오인식이 반복될 수 있다.

원문을 타이핑으로 수정한 뒤 재인식하면 수정 내용은 새 인식 결과로 바뀐다. 수정한 내용을 번역하려면 **재인식이 아니라 번역하기**를 누르면 된다.

실패·취소 후 다시 시도하거나, 추후 모델·설정을 바꾼 뒤 같은 녹음을 비교할 때 의미가 있다.

## 지금의 한글 발음은 어떻게 만들어지나

현재는 다음 두 방식을 함께 쓴다.

1. LLM에 확정된 영어 문장을 보내 한글 발음을 직접 생성하도록 요청한다.
2. 프로그램이 JSON 형식, 빈 값, 길이, 허용 문자 등을 검사한다.

별도 사전으로 단어를 찾아 바꾸거나, 영어 발음 기호를 한글로 변환하는 로직은 없다. 잘못된 발음을 자동으로 교정하지도 않는다.

예를 들어 `come`에 대해 모델이 ‘콜럼’을 내놓으면 한글 형식이므로 통과할 수 있다. 반면 로마자나 허용하지 않은 문자가 섞이면 실패 처리한다. **형식 검증은 발음의 정답 검사와 다르다.**

앞으로 발음 사전이나 G2P(지투피, 철자에서 음소로 변환)와 한글 표기 규칙을 검토할 수 있다. 번역과 발음 처리를 별도 모듈로 나누면 번역 모델을 바꾸더라도 발음 규칙을 유지하기 쉽다. 다만 고유명사·숫자·축약형 등은 별도로 검증해야 하고, 모듈을 나누는 것만으로 정확해지지는 않는다.

## 내가 시험한 세 가지 사례

### 1. 원문이 맞아도 다음 단계에서 실패할 수 있다

첫 화면에서 나는 말한 내용과 한국어 원문이 같다고 확인했다. 그러나 영어·발음 생성 실패가 표시됐다.

코드를 확인한 결과 해당 문구는 최종 결과 검사에서 발생한다. 영어는 먼저 검사하므로 발음 결과의 조건 위반이 의심된다. 당시 모델 응답을 저장하지 않아 정확히 어떤 문자나 값 때문에 실패했는지는 알 수 없다.

현재는 영어와 발음을 한 쌍으로 반환하므로 발음 단계가 실패하면 영어도 표시하지 않는다. 빈 영어 영역만 보고 영어 번역 자체가 실패했다고 단정하면 안 된다. 실패 단계가 명확하지 않은 화면 안내도 개선할 부분이다.

### 2. A 거점이 Agar point로 바뀐 과정

```text
말한 문장: A 거점에서 막자
인식 원문: 에이거점에서 막자
영어: Hold at the Agar point.
발음: 홀드 어트 어거 포인트
```

Whisper가 바로 ‘어거 포인트’로 인식한 것은 아니었다. 먼저 ‘에이거점’이라는 표기가 만들어졌고, 번역 단계에서 이를 `Agar`라는 이름처럼 해석했다.

다음에는 원문을 `A 거점에서 막자.`로 정확히 수정한 뒤 번역해 보면 된다. 수정 후 개선되면 입력 표기의 영향이 컸다는 근거가 된다. 여전히 잘못되면 번역 모델 쪽 문제도 더 살펴봐야 한다. 이 비교 시험은 오늘 아직 하지 않았다.

### 3. 다른 번역기와 문장이 다르면 오역인가

앱은 다음 문장을 표시했다.

> I need to head to Ark Station now. Do you know where that is?

비교한 번역기는 다음과 같았다.

> I need to go to the Ark Station right now. Do you know where that is?

`head to`는 ‘그곳으로 향하다’, `go to`는 ‘그곳으로 가다’라는 의미다. `right now`는 즉시성을 좀 더 강조한다. 표현은 다르지만 핵심 의미는 비슷하다. 장소 이름이라면 `Ark Station`처럼 관사 없이 쓰는 것도 가능하다. 실제 게임의 공식 영문 지명인지는 따로 확인해야 한다.

반면 화면의 `where that is`에 대응하는 ‘웨어 쑤어 티즈’는 부정확했다. 영어 번역이 괜찮아도 한글 발음까지 괜찮은 것은 아니다. 앞선 설명에서 ‘Do you know’의 ‘유’가 빠졌다고 했던 부분은 Codex의 화면 오독이었다. 화면에는 ‘두 유 노우’가 있어 누락 사례로 기록하지 않는다.

## 모델을 바꿀 때 코드 전체를 다시 만들지 않으려면

Interface(인터페이스, 공통 사용 규약)를 두어 화면이 구체적인 모델 사용법을 몰라도 되게 한다.

| 코드 | 역할 |
| --- | --- |
| `Speech/ISpeechRecognizer.cs` | 음성 → 원문이라는 공통 요청 |
| `Speech/LocalWhisperRecognizer.cs` | 실제 로컬 Whisper 실행 |
| `Translation/ITranslationService.cs` | 한국어 → 영어·발음 결과라는 공통 요청 |
| `Translation/OllamaTranslationService.cs` | 로컬 모델 요청과 결과 검사 |
| `MainWindow.Translation.cs` | 번역 버튼·취소·원문 변경 시 결과 지우기 |

표의 경로는 `src/GameLanguageAssistant/` 아래에 있다. Ollama 구현은 생성자로 모델 이름을 받는다. 외부 API를 사용할 때는 같은 인터페이스를 구현하는 서비스를 만들고 연결하면 된다. API 인증·오류·요금 처리는 그때 추가해야 하므로 설정만 바꾸면 이미 외부 API가 동작한다는 뜻은 아니다.

## 비동기 작업에서는 오래된 결과가 늦게 올 수 있다

Async(어싱크, 비동기)는 처리를 기다리는 동안 화면이 멈추지 않게 하는 방식이다. 그 사이 사용자가 원문을 고치거나 창을 닫을 수 있다.

이때 옛 원문의 번역이 늦게 도착해 새 원문 아래에 표시되면 혼란이 생긴다. 현재 코드는 취소 요청과 버전 확인으로 그런 결과를 버린다. 모델 호출 자체가 끝나는 것과 그 결과를 화면에 적용할지는 구분해서 처리한다.

Whisper는 실행 중 강제 취소 검사에서 네이티브 엔진 종료 문제가 발생했다. 현재는 내부 계산이 끝난 뒤 취소 결과를 버리므로 취소 완료까지 기다릴 수 있다. ‘취소 버튼이 있다’와 ‘계산이 즉시 멈춘다’는 같은 뜻이 아니다.

## 다음 테스트를 어떻게 기록할까

한 번에 전체 결과만 보지 말고 다음처럼 나눠 비교한다.

| 말한 문장 | 인식된 원문 | 직접 수정 여부 | 영어 결과 | 한글 발음 | 인식·번역 시간 |
| --- | --- | --- | --- | --- | --- |
| A 거점에서 막자 | 에이거점에서 막자 | 없음 | Hold at the Agar point. | 홀드 어트 어거 포인트 | 약 0.9초 / 0.5초 |

- 같은 녹음 재인식과 새로 말해 녹음하는 시험을 구분한다.
- 번역만 평가할 때는 인식 원문을 정확하게 수정하고 시작한다.
- 긴 문장을 전체와 문장별로 나눠 비교한다.
- 숫자·방향·부정·고유명사를 확인한다. 예: ‘오른쪽에 두 명’, ‘들어가지 마’, ‘탄약이 부족해/없어’.
- 번역기를 정답지처럼 보고 문구 일치만 확인하지 않는다. 실제 의미가 보존됐는지를 본다.
- 첫 모델 로딩과 연속 실행의 시간을 구분한다. 화면의 처리 시간은 말하는 시간까지 포함한 전체 대화 지연이 아니다.

## 오늘의 도달점과 남은 것

로컬 음성 인식부터 번역 표시까지 기능 흐름은 연결됐다. 하지만 게임 용어 해석, 실패 단계 안내, 한글 발음의 정확성은 아직 부족하다. 새 기능을 추가하기 전에 기존 시험을 단계별로 나눠 원인을 더 확인하기로 했다.
